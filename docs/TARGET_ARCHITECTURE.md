# Целевая архитектура Unreal Codex Harness

Статус: принятое направление развития после версии 0.1.

## 1. Цель

Харнесс должен быть расширяемой платформой автоматизации Unreal Editor, а не каталогом из сотен узкоспециализированных JSON-команд. Стандартные операции должны выражаться небольшим набором универсальных примитивов. Подсистемы с собственными моделями данных и схемами графов подключаются через адаптеры, сохраняя единый контракт выполнения, безопасности и результата.

Цель не формулируется как «90% всех функций Unreal Engine». Измеряемая цель — покрытие 80–90% выбранного набора типовых редакторских сценариев после появления универсального ядра, рецептов и приоритетных адаптеров.

## 2. Основные принципы

1. **Инспекция перед изменением.** Клиент сначала получает типы, свойства, функции, фабрики, ноды и доступные возможности.
2. **Универсальные примитивы вместо one-off actions.** Новый пользовательский сценарий по возможности оформляется рецептом, а не новым обработчиком Python/C++.
3. **Типизированный JSON.** UObject-ссылки, классы, enum, структуры, контейнеры и вложенные объекты имеют однозначное представление.
4. **Безопасность по умолчанию.** Полная предварительная валидация, транзакции, `dry_run`, явное сохранение, ограниченные результаты и запрет неаудируемого кода.
5. **Обнаружение возможностей во время выполнения.** Клиент не предполагает наличие функции, типа ассета или ноды и использует каталоги возможностей.
6. **Версионные границы.** Публичное ядро ориентируется на UE 5.8. Адаптеры, использующие внутренние API, явно объявляют точную совместимость.
7. **Единый результат.** Ядро и все адаптеры возвращают одинаковый envelope `result.json`, диагностические коды и сведения об изменённых объектах.

### 3.1 Протокол и исполнитель

Сохраняется существующий документ `format_version: "1.0"`, зависимости между командами и последовательное выполнение. Исполнитель отвечает за:

- валидацию всего документа до первой мутации;
- разрешение ссылок на результаты предыдущих команд;
- транзакции Undo;
- `dry_run` и план выполнения;
- атомарную запись результата;
- лимиты команд и размера ответа;
- перечень изменённых пакетов и объектов;
- стабильные коды ошибок, не зависящие от локализации редактора.

### 3.2 Типизированный JSON codec

Codec преобразует JSON в `FProperty` и обратно. Обязательные категории:

- scalar: `bool`, integer, float, string, name, text;
- enum и bitmask;
- UObject, class, soft object и soft class reference;
- struct, включая `Vector`, `Rotator`, `Transform`, `Color`, `Key`;
- array, set и map;
- optional/nullable значения;
- instanced subobject только при явно разрешённом владельце и классе.

Каждая неоднозначная величина должна иметь явную форму, например:

```json
{"$type":"object","path":"/Game/Input/IA_Jump.IA_Jump"}
```

### 3.3 Универсальные объектные операции

Целевые примитивы:

- `object.describe` — класс, свойства, функции и ограничения;
- `object.inspect` — типизированные значения выбранных свойств;
- `object.set` — изменение одного или нескольких свойств через codec;
- `object.call` — безопасный вызов разрешённой `UFunction` с входными и выходными параметрами.

`object.call` не является произвольным исполнением кода. Разрешение определяется политикой по классу, модулю, метаданным функции и режиму редактора. Latent, сетевые, консольные, файловые и потенциально разрушающие вызовы запрещены, пока для них не появится отдельная политика.

### 3.4 Универсальные операции с ассетами

Целевые примитивы:

- `asset.search` и `asset.inspect`;
- `asset.describe_types` — доступные классы и фабрики;
- `asset.create` — создание через подходящую `UFactory`/Asset Tools;
- `asset.duplicate` — безопасное копирование без замены назначения;
- `asset.save` — явное сохранение пакетов.

Удаление и безусловная замена ассетов не входят в безопасное ядро.

### 3.5 Универсальная работа с графами

Графовый API не должен зависеть от отображаемого текста ноды:

- `graph.describe` — схема и backend графа;
- `graph.search_nodes` — контекстный поиск через каталог действий;
- `graph.describe_node` — стабильная спецификация, пины и требования;
- `graph.add_node` — создание по спецификации каталога;
- `graph.connect` — соединение с проверкой схемой Unreal;
- `graph.set_pin_value` — типизированное значение литерального пина;
- `graph.inspect` — ноды, пины, связи и диагностика.

Для K2 каталог строится на Blueprint Action Database и Node Spawners. Material, Niagara, Control Rig и другие схемы предоставляют те же операции через собственные backend-адаптеры.

### 3.6 Реестр адаптеров

Адаптер регистрирует:

- уникальный `backend_id`;
- поддерживаемые классы объектов и графов;
- объявление возможностей и версии UE;
- обработчики только тех операций, которые нельзя выразить ядром;
- валидатор, инспектор и диагностические коды;
- набор автоматических контрактных тестов.

Выбор адаптера выполняется по типу объекта/графа. Поле `backend` используется только для устранения неоднозначности, а не как обязательная деталь каждого запроса.

### 3.7 Рецепты

Рецепт — декларативная композиция универсальных команд с параметрами и ссылками на результаты. Примеры: настройка Enhanced Input, интерактивная дверь, здоровье персонажа, базовый AI Controller.

Рецепты не получают доступ к Python или shell. Они проходят ту же предварительную валидацию, поддерживают `dry_run` и должны быть идемпотентными либо явно сообщать конфликт существующего состояния.

## 4. Границы применимости

Архитектура предполагает интеграцию практически с любой подсистемой, имеющей публичный Editor API, UObject/UFunction, фабрику или расширяемую схему графа. Она не гарантирует автоматическую поддержку:

- внутренних C++ API без отражения;
- возможностей, доступных только через Slate UI;
- закрытых сторонних плагинов;
- runtime-функций, не имеющих смысла в редакторской автоматизации;
- API, требующих модификации исходного кода движка.

Для таких случаев применяется специализированный адаптер, UI-автоматизация как крайний вариант либо фиксируется невозможность безопасной поддержки.

## 5. Политика добавления функций

Перед добавлением нового публичного action необходимо последовательно проверить:

1. Выражается ли операция существующим `object.*`, `asset.*` или `graph.*`.
2. Можно ли оформить её как рецепт.
3. Нужен ли backend для отдельной схемы графа или специализированного Editor API.
4. Только если предыдущие варианты не подходят — оправдан ли новый верхнеуровневый action.

Таким образом предотвращаются дублирование и разрастание командного API.

## 6. Текущее состояние версии 0.1

Уже реализованы пакетная валидация, зависимости, `dry_run`, транзакции, атомарный результат, инспекция части объектов, базовые операции с ассетами и уровнями, а также K2-графы с ограниченным набором видов нод.

Главные отсутствующие части целевой архитектуры: общий типизированный codec, безопасные `object.*`, фабричный `asset.create`, Blueprint Action Catalog, backend registry и recipes runtime. Порядок их реализации определён в [ROADMAP.md](ROADMAP.md).
